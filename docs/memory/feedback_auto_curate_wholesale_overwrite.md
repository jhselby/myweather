Rule: when a runtime JSON is both (a) auto-regenerated by a digest-time script and (b) hand-populated for some fields, the hand-populated cells will be silently wiped on the next digest run. Any ship that manually edits such a file must simultaneously extend the auto-curate script to preserve or re-emit those cells.

**Why:** 09-30 incident — v0.7.15 shipped 5 sr learned_gbm cells into `weather_collector/data/l1_learned_selector_curated.json` by hand (sourced from the v5 sweep). The daily `l1_learned_selector_curate.py` had `FIELDS = ("t", "h")` and knew nothing about sr. The 09-30 06:22 digest regenerated the file wholesale with `cells: []`, and the 08:57 v0.7.17 collector redeploy baked the empty file live. v0.7.15 was a working ship for ~19 hours, then became a silent no-op without any flag or alert — detected only by [[feedback_shipped_flag_verify_effect]] pair-log inspection in the afternoon.

Fixed in v0.7.18 by splitting curate into `V2B_FIELDS` and `V5_FIELDS`, with sr sourced from `l1_learned_selector_curated_v5_candidate.json`.

**How to apply:**
- When manually editing a `*_curated.json` or similar runtime table, immediately `grep -rln <filename>` to find the WRITER. If a writer exists in `analysis/`, confirm it either (a) includes the field being added, or (b) is modified in the same ship to preserve the manual cells.
- A curated JSON file with `generated_at` or `fitted_at` ISO timestamp in it is almost certainly auto-regenerated. Treat as a time-bomb unless you've verified the writer logic.
- When verifying a flag ship on pair-log, also sanity-check that the on-disk curated JSON still has the expected cells at the time of verify. The file timestamp + cell count tells you if a digest wiped it.
